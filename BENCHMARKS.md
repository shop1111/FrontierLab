# Reproducible Benchmarks

Measured on Windows with `moonc 0.10.18+6c83a7f62`, native debug target, using
one sequence entity and full scene snapshots. Times are milliseconds from one
local run on 2026-10-31; rerun before quoting results on another machine.

```bash
moon run bench --target native -- 100 1000 10000 50000
```

| Steps | Build | Encode | Decode | HTML | Diff | Contract | Divergence | JSON bytes | HTML bytes |
|---:|---:|---:|---:|---:|---:|---:|---:|---:|---:|
| 100 | 1 | 1 | 2 | 2 | 0 | 0 | 0 | 44,340 | 81,519 |
| 1,000 | 3 | 17 | 21 | 18 | 0 | 0 | 2 | 440,340 | 477,519 |
| 10,000 | 28 | 149 | 177 | 176 | 0 | 4 | 10 | 4,409,340 | 4,446,519 |
| 50,000 | 196 | 875 | 898 | 936 | 0 | 22 | 60 | 22,089,340 | 22,126,519 |

HTML bytes grew by a constant ~28 KB per page against the 0.10.4 run because
the v0.9.1 player embeds more styles and scripts; trace data size is unchanged.
Memory was not re-measured for this run. The 50,000-step case uses explicit
`TraceOptions` for both build
and decode. CI only runs 100/1,000-step correctness smoke tests and intentionally
has no fragile millisecond threshold.

`Diff` compares the final two frames, `Contract` runs sequence-transition over
the complete trace, and `Divergence` compares the trace with itself. Schema v1
uses complete snapshots, so JSON/HTML size grows roughly linearly.

## Tracing overhead and complexity profiles

Generated by `moon run examples/complexity_profile --target native` on Windows
with `moonc 0.10.18+6c83a7f62` (native debug) on 2026-11-01. Operation counts
are deterministic; timings are from one local run.

Complexity profiles use `profile_traced_array` at `TraceLevel::Count` on a
deterministic permutation of `0..<n`, fitting the compare count for
n = 128, 256, 512, 1024, 2048:

| Algorithm | compares at n = 2048 | best fit | relative error | empirical exponent |
|---|---:|---|---:|---:|
| Bubble sort | 2,096,128 | O(n^2), 0.498 · n^2 | 0.3% | 2.00 |
| Insertion sort | 983,104 | O(n^2), 0.241 · n^2 | 2.8% | 1.97 |
| Heap sort | 38,921 | O(n log n), 1.652 · n log n | 3.2% | 1.20 |

The runner-up class is at least 19% off in every case, so the best fit is well
separated.

`measure_tracing_overhead` on insertion sort with n = 64 (2,050 trace steps):

| Level | ms per run | vs Off |
|---|---:|---:|
| Off (plain operations) | 0.0308 | 1.00x |
| Count (counters only) | 0.0352 | 1.14x |
| Full (trace and `finish`) | 151 | about 4,900x |

`Count` adds about 14%, so counters can stay enabled in ordinary runs. `Full`
costs about 74 µs per step and produces 14.6 million JSON characters, because
Schema v1 stores a complete 64-element snapshot at every step; keyframe plus
delta storage is the planned remedy.
